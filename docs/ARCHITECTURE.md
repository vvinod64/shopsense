# ShopSense — Architecture Review (Milestone 8)

*Template: Day 4 Session 2, "Architecture review write-up". Capstone problem statement 4 — Customer Care & Order Operations Assistant for the Kartway marketplace.*

## System overview

ShopSense resolves e-commerce support tickets (order status, late delivery, damaged items, refunds, policy questions) for Kartway. A customer message is parsed, checked against the Kartway policy corpus and the order system, and turned into a proposed action (refund / replacement / information) and a customer reply. Routine, low-risk tickets resolve automatically. Anything risky — refunds above the ₹2,000 automated cap, angry customers, legal threats, safety reports, prompt-injection attempts, account-status questions, an unavailable order system — parks at a human-approval gate and is executed only after an authenticated reviewer whose refund-matrix tier covers the amount approves it.

**The single most important job:** never auto-approve a refund the policy does not allow, and never tell a customer a policy fact (window, fee, amount) that is not in the policy documents.

## Components & data flow

```
customer message
  -> M1 triage (LiteLLM + Pydantic SupportTicket, bounded repair loop)
  -> M5 policy_check: order system (robust: breaker -> retries -> human-queue fallback), order ownership
                      + policy RAG (Qdrant Cloud dense, Gemini embeddings, BM25 + RRF, cross-encoder rerank;
                        the governing document of each risk rule and the ticket's category addendum are added)
                      + M3 memory (stored preferences, recent tickets) and ledger (third-contact count)
                      -> risk list (deterministic, includes refund-eligibility blockers)
  -> propose action: code picks the action; amount and eligibility from the policy-grounded calculator
  -> draft reply (LLM) -> checks (all reply guardrails, before anything executes) -> revise (LLM, max 2)
  -> route (pure function): auto -> finalize | risky -> human approval (interrupt, SqliteSaver)
  -> finalize: the only irreversible step (refund/replacement request, idempotent); the order system's
     status decides (a request it holds is not executed without a human); after an approval the customer
     gets a reply written from the executed outcome; ledger + episodic memory
  -> M8 guardrails on the way out (schema, injection, refund cap, fabrication) -> FastAPI
     -> web pages per role: customer chat (signed-in customer or guest) and support console (staff sign-in)
```

| Component | Module | What it does | Failure mode if this breaks |

## Design decisions

**Model and context budget.** Gemini `flash-lite` through LiteLLM: the course stack, a free tier, and fast enough for a support reply; any LiteLLM model string can replace it (see `.env.example`), and the decision rule is the course's one: the cheapest model that passes the golden set. Measured on the 20-ticket run `run-141913` (Langfuse): about 2 model calls per ticket (triage and draft, plus a revision when the reply checks fail), a median of about 1,660 input and 200 output tokens, about $0.0007 per ticket at list price, so 500 tickets a day would cost about $0.38. What goes into each call is decided per call: the system prompt, the facts the code computed (order, quote, risk, memory), the three reranked policy sections tagged with their source, and the rolling summary instead of the full conversation (M3 working memory, budget-triggered summarisation that is tested to keep order references).

**Graph, not a chain.** Tickets branch (automatic or a person), loop (revise at most twice) and wait for a human for hours, possibly across a restart; those are graph features (conditional edges, `interrupt()`, SqliteSaver checkpoints). A straight chain would have none of them. Raw LangGraph rather than a batteries-included harness, for control over each state field and the order of checks.

**One team and one workflow, both servable.** The API serves the multi-agent team (M6) by default, because the problem statement asks for a multi-agent assistant whose mandatory components are its agents; it costs about 12 model calls per ticket (1-1.5 minutes on the free tier). `SHOPSENSE_ENGINE=workflow` serves the single orchestrated workflow (M5) instead (2-3 calls, easier to trace), with the same durable approval flow. In the team a risky ticket pauses at an `interrupt()` approval node (LangGraph `AsyncSqliteSaver`, `runtime/team_checkpoints.sqlite`), survives a restart, and is resumed from any process by the same reviewer endpoints; an approval executes the held request once, a rejection executes nothing, and "changes requested" sends the reviewer's note back to the drafting agent and through both checks again. Verified live over HTTP: angry ₹12,999 ticket held (202), server restarted, still pending, approved by an Operations Manager (200, refund executed once, outcome reply), replay 409. The team earns its coordination cost through separation of duties rather than speed: the Fact-Checker never sees the customer's message, each agent can write only its own fields, and the supervisor's loop-backs and the team's model-call budget are capped. Both run the same golden set.

**Protocols.** MCP for tools: the order system is one MCP server (8 tools, 2 resources, no delete or approve tool, the ₹2,000 cap enforced inside it) used by two clients (the team and an email agent); it sits at the edge, so leaving MCP costs one adapter. A2A is not used: all agents run in one process and one organisation. AG-UI is not used: the API is request/response, with 202 plus `/tickets/pending` for long waits. The AP2 idea (provable authority) appears as the approval record: reviewer token, approver name and refund-matrix role are checked before anything runs, and the decision is stored in the checkpoint; it is not cryptographically signed.

**Retrieval, not fine-tuning.** Policies, windows and fees change, and every answer must cite the current text, so they are retrieved. Stable behaviour (tone, length, no policy codes) is set by the prompt and enforced by the reply checks; no fine-tuning was needed to pass the golden set.

**Learning from reviewers.** When a reviewer rejects a reply or asks for changes with a note, the note is kept as a lesson for that issue type (`m3/memory.py`, `lessons` table: duplicates merged, newest three used) and given to the drafter on later tickets of the same kind, in both the workflow and the team.

## Guardrails & safety

**Covered**
- Refund cap: approval is decided in code (`mock_api.create_refund_request`, also behind the MCP server); the reply oracle rejects "approved/processed" claims while a human must decide; the output guardrail blocks any auto-approved refund above ₹2,000 (HTTP 422).
- Policy fabrication (the same check audits the golden set's expected answers, `m8/golden_audit.py`): every ₹ amount must equal the quote or order value; every days / hours / months / percent figure must appear with the same unit in the retrieved policy or order data, and when the sentence names a product category it must come from that category's addendum or the general policy (so "Electronics: 45 days" is caught although Apparel's addendum says 45); a range ("4 to 7 business days") must match a band the policy states; spelled-out numbers count. These checks run inside the workflow before anything executes, and again at the API; a failing reply is revised (max 2) and then goes to a human. Approver edits get the same checks. A figure is also tied to its subject: it must come from a policy sentence on the same topic (return window, warranty, restocking fee, transit, reporting deadline, goodwill), so warranty "12 months" cannot back a "return within 12 months"; and when the sentence names a category whose addendum states a figure for that topic, the general-policy figure is not accepted ("Electronics … 30 days" is blocked, 15 is required) unless that clause explicitly compares with the general policy. A figure an addendum quotes only to override it ("Notwithstanding the standard 30-day window …") counts as a general figure, not the category's.
- Refund eligibility (order system, every transport): a change-of-mind return outside the category window (Beauty 14, Electronics 15, Home & Kitchen 30, Furniture 42, Apparel/Sports/Toys 45 days) and a "not delivered" claim (needs the 7-day no-scan threshold and a courier tracer, Shipping policy 4.3) never auto-approve; the blockers become risk reasons and the reply explains them.
- Who the customer is: the customer comes from a signed session token issued at sign-in (`/auth/customer`; in the demo the password is the customer id), never from what the browser or request body claims; naming a customer without their token is refused (401). A customer's held ticket is visible only to that customer. Without a token the caller is a guest.
- Order ownership: a signed-in customer quoting another customer's order gets no order facts and goes to a human; memory is read only for the signed-in customer.
- Prompt injection, three layers: patterns (the course regex, extended), Meta's Llama Prompt Guard 2 classifier (served by Groq; a probability per text, windowed for long texts) and, for customer messages, a reviewer-model judgement that must quote the manipulating words (code checks the quote is in the message). A pattern hit holds the ticket; a classifier flag is confirmed or cleared by the judge when it is available. Injected tickets and injected policy text are held for a human, and ticket text is always passed to models inside an "untrusted data" block. Measured on 78 labelled tickets (`python -m shopsense.guardrails --injection`, `eval/injection_cases.json`: 14 intake injections, the 4 golden injections, 8 reworded attacks, 46 ordinary intake tickets and 6 innocent look-alikes): patterns 15/26 detected, 0/52 false alarms; classifier 18/26, 1/52; judge (`gpt-oss-120b`) 26/26, 0/52; as deployed 26/26 and 0/52. The classifier found four real injections in the course's intake data that the patterns miss (SHOPSENSE-00044, -00050, -00085, -00183), first mislabelled as benign. With `gpt-oss-20b` as the judge: 25/26 and 1/52 (cheaper, slightly weaker).
- Damage on arrival: a reply may not hold the "free of physical damage" return condition against a customer who reports that the item arrived damaged or defective (that condition is for change-of-mind returns; damage on arrival is a Kartway or merchant error, returns policy §2.10).
- Liability admission and account-flag disclosure: deterministic phrase checks from Escalation standard §4 and Fraud standard §4.4. The flag rule applies to every reply, flagged account or not: §4.4 forbids disclosure "directly or indirectly".
- Promises no phrase list foresees: a reviewer model (`REVIEWER_MODEL`, a different provider: `groq/openai/gpt-oss-120b`) lists every commitment in a reply and must quote the evidence that supports it; code accepts a commitment only if the quote really occurs in the policy excerpts or computed facts (allowing small copying slips), money promises on an order must match the computed quote (an amount-less promise cannot be checked against a partial quote, so it is flagged), statements that only promise a follow-up or review are never treated as commitments, and a flag counts only when a second pass confirms it. It runs inside the workflow's checks and the team's fact-checker before anything executes; if the model cannot be reached, the reply goes to a person.
- Measured in both directions: `python -m shopsense.guardrails --eval [--live]` runs 34 labelled replies built on real policy clauses (`eval/guardrail_cases.json`): 16 good replies that must not be blocked and 18 bad ones that must be, 6 of them reworded promises ("we'll make sure you're not out of pocket", "we'll skip the packaging fee", an invented technician visit). Rules only: false rejections **0/16**, false approvals 4/18 (four of the rewordings; the rules now also catch "skip the fee" and favours framed as "a one-time courtesy"). Rules plus the reviewer model: **0/15** and **0/18** in two runs on the first 33 cases; the latest run, with the computed-goodwill-credits case added, gave **0/16** and 1/18, the miss being the "skip the packaging fee" reply, which a rule now catches without the model. Building the set found two real issues, both fixed and kept as tests: an account-flag disclosure that passed because that account was not flagged, and early versions of the model check that blocked good replies or let paraphrases through (fixed by verified quotes, the money rule and two-pass confirmation). On the 20 golden-set tickets, guardrail_passed is 1.000, so no real reply was blocked.
- Non-numeric promises: "full refund", "no fees/deductions" must match a quote equal to the order value (or, with no quote, the retrieved policy); "regardless of condition" / "no questions asked" must appear in the policy text. Negated uses ("not a full refund") are allowed. Without a quote, the promise must match the clause's condition: a change-of-mind or opened-item promise is never backed by a defective/damaged-item clause, and a promise about a specific order needs a quote.
- Checked before anything executes: the M5 `checks` node runs the same reply checks the API applies (`reply_problems`: response schema, amounts, figures, promises, liability, disclosure) and injected policy text becomes a risk that sends the ticket to a human; edited replies go through the same checks. Every model call has a 60 s timeout (`LLM_TIMEOUT_SECONDS`; LiteLLM's default is 6000 s).
- Human-in-the-loop: refunds above the cap, angry sentiment, legal threats, safety reports, third contact in 14 days (counted in the ledger, or stated by the customer: "third time I'm writing"), explicit human requests, account-status questions, unavailable order system.
- M2 single agent: its escalation triggers (angry customer, legal, safety, above the cap, third contact, pause, …) are passed by the tool layer to the order system as hold reasons, so a refund the model requests on such a ticket is held for a person even when the amount is small; the model is told to escalate, the tool layer makes sure.
- A completed ticket is never turned into an error by memory: the conversation summary drops old turns only after the summariser succeeds, and if saving the session fails the API still returns the ticket's result.
- Who may approve: the decision endpoints require a reviewer token (a staff session from `/auth/staff`, a named reviewer's token or an SSO token); `approver` must be the authenticated reviewer; an approval is refused (403) unless the reviewer's role covers the amount under the Refund Authorisation Matrix (Team Lead ≤ ₹10,000, Operations Manager ≤ ₹50,000, Finance above). An approver-edited reply runs through the same reply checks before the ticket resumes; a failing edit is refused with 409 and the ticket stays parked.
- After the decision: an approved refund/replacement gets a deterministic confirmation reply built from the executed request (amount and order from the order system, not the model); a rejection replaces the holding reply; an out-of-stock replacement is handed back to a person instead of being confirmed.

**Still open**
- The corpus contradicts itself on the cap (`refund-authority.md` ₹2,000 vs `escalation-tone.md` "$50 USD"); ShopSense treats the INR matrix as authoritative.
- The SSO path verifies OIDC tokens against the issuer's published keys and is tested with locally signed tokens; it has not been connected to a real company identity provider.
- The model-based checks (commitments, injection judge) run on a free Groq tier with a daily token cap (200,000 tokens a day per model for `gpt-oss-120b`, roughly 70 tickets at ~2,700 tokens each); when the cap is reached they fail safe (the reply or ticket goes to a person), which on a busy day means more tickets for people. A paid tier or a self-hosted model removes the cap.

## Known limitations

- Data provenance: `data/` is the toolkit output, unchanged. The golden set the system is graded on is `eval/golden_set_v2.json`, derived from `data/shopsense/eval/golden_set.json`; `eval/manifest.json` records why it replaced the generator output (category mix 7/3/1/5/4 against the guide's 6-7/5-6/3-4/3/2 for factual/guardrail/injection/multi-hop/unanswerable; v2 is 6/5/4/3/2) and every corrected answer.
- The intake stream is harsher than the guide's suggested ratios: 1 in 3.6 records angry (guide: 1 in 8), 1 in 3.5 missing the order reference (guide: 1 in 6), 82 of 200 claiming more than ₹2,000 (guide: two or three). It exceeds every minimum, so it tests escalation and missing-field handling more heavily than the guide asks; M1 accuracy is measured on its first 20 records.
- Parser accuracy on the first 20 intake records: issue type 85%, order id 100%, sentiment 75%, needs-a-human 70% with no risky ticket marked routine (FN 0); all six disagreements are the parser asking for a person where the dataset label does not. On the 48-record sample in the guide's ratios: issue type 91.7%, sentiment 72.9%, needs-a-human 85.4%. Account-access requests go to a person, because no tool can change an account.
- Free-tier Gemini (15 requests/minute) forces a 4–4.5 s pause per LLM call; a ticket takes ~15–60 s.
- The intake records' order/customer references do not exist in the mock tables, so end-to-end tests use real orders from the tables instead.
- The provided `data/shopsense/eval/golden_set.json` was model-generated and several expected answers contradict the corpus (e.g. Electronics 14 vs 15 days, groceries 24 h vs 4 h, furniture 30 vs 42 days); `eval/golden_set_v2.json` corrects them and documents each change.
- Hybrid retrieval does not beat dense on the Markdown corpus (MRR 0.967 vs 1.0) but does on the lossy PDFs (recall 0.956 dense vs 0.978 hybrid); BM25 is also kept for exact-token guarantees.
- The PDF renderer has no rupee glyph ("₹2,000" is extracted as "■2,000"); ingestion restores ₹ before numbers.
- Return windows are measured from the delivery date (placed_at + actual_delivery_days) to today; set `SHOPSENSE_AS_OF=YYYY-MM-DD` for reproducible runs. Most mock orders were delivered months ago, so change-of-mind returns mostly go to a human.
- Supermemory's memory-extraction layer lags behind ingestion; recall falls back to its document layer meanwhile.
- Canaries, SLOs and alerts run from cron or `--every`; there is no hosted dashboard beyond Langfuse's own (canary scores and alerts are files and Langfuse scores).

## Deployment notes

- **Secrets:** `.env` (git-ignored; `.env.example` lists every key): Gemini, Groq (independent reviewer and judge), Supermemory, Qdrant Cloud and Langfuse; optionally a fixed reviewer token for scripts and the session-signing secret (generated in `runtime/` when unset). No key appears in code or logs.
- **Data:** `data/` is read-only input and is exactly the generator toolkit's output; everything written at runtime goes to `runtime/` (ledger, action/escalation logs, LangGraph checkpoints, chat sessions, eval reports), overridable with `SHOPSENSE_RUNTIME_DIR`. Clear `runtime/` before a live demo: refunds recorded by earlier runs make the order system hold a repeat request for the same order.
- **Run:** `uv run shopsense` (API and web pages on port 8000, demo state in `runtime/demo`), then http://localhost:8000/ui; public demo via `ngrok http 8000` (needs an ngrok authtoken).
- **Rate limits:** LiteLLM `num_retries`, ChatLiteLLM `max_retries`, per-call pacing, and the eval's shared gate honouring Gemini's `retryDelay`. The API returns **503 + `Retry-After`** (not 500) when the provider is rate-limited. Free-tier quotas are per model (15 requests/min, 500/day for `gemini-3.5-flash-lite`); `SHOPSENSE_LLM_MODEL=gemini/gemini-3.1-flash-lite` switches model for one run without editing `.env` — the final live API test ran that way after the daily quota of the default model was spent.
- **Model-dependent wording:** on `gemini-3.1-flash-lite` a routine auto-approved reply once added "this request is being reviewed by our team"; the reply oracle blocks the opposite error (claiming approval while a human must decide) but not this over-cautious wording.
- **Operations runbook:** *pause* with `SHOPSENSE_AUTOMATION=paused` and a restart: tickets are still triaged and drafted, but every one waits in `/tickets/pending` and nothing executes. The pause is enforced in the order system itself (`mock_api`): while it is set, every refund or replacement request is created as held for a person, whichever client asks (workflow, agent team, M2 agent, MCP server, email agent); a reviewer's approval still executes. *Investigate* in Langfuse by session (= ticket id) or by tag; each trace carries the model and a prompt version (a hash of the system prompts), so a bad reply can be tied to the prompt that wrote it. *Roll back* by reverting the release; the prompt version in new traces confirms the old prompts are back. *Learn*: reviewer notes on rejected or returned replies become lessons for that issue type. *Expire*: a held ticket waits at most `SHOPSENSE_APPROVAL_TTL_HOURS` (72); `python -m shopsense.m5.workflow --expire-overdue` (hourly from cron) or `POST /tickets/expire` closes overdue tickets of both engines without executing anything, tells the customer a person will follow up and records an escalation so one does; `/tickets/pending` shows each ticket's age and an `overdue` flag. *Watch*: `python -m shopsense.m7.canary` runs canary tickets with known answers (default SS-F02, SS-G04, SS-I01) through the live system in a throwaway runtime and checks SLOs (canary pass rate 100%, p95 latency ≤ 120 s, cost ≤ $0.01 per ticket, error rate 0); a breach writes `runtime/alerts/alert_*.json`, posts to `SHOPSENSE_ALERT_WEBHOOK` (Slack-compatible) and exits 2; `--every 60` or cron runs it continuously. First live run: 3/3 passed, p95 25.4 s, $0.0015 per ticket. *Reviewers*: named reviewers each have their own token (stored only as a SHA-256 hash) and refund-matrix role (`python -m shopsense.m8.api --add-reviewer NAME ROLE`); with `SHOPSENSE_OIDC_ISSUER` set, signed SSO tokens (OIDC JWT) are verified against the issuer's keys (signature, issuer, audience, expiry) and the reviewer's name and role come from the token. In the demo, staff sign in on `/ui` with one account per refund-matrix role (`lead`, `ops`, `finance`; password = username; `SHOPSENSE_DEMO_STAFF=off` removes them); the optional `.env` reviewer token serves scripts.
- **Trace data:** redacted before it leaves the process (Langfuse `mask`: emails, UPI ids, phone numbers, card/Aadhaar, PAN, IFSC and bank account numbers, card endings, dates of birth, and passwords/OTPs/PINs/CVVs; order and customer references, amounts and ordinary dates are kept because traces are searched by them). Names are redacted after introductions, titles and sign-offs ("my name is …", "Mrs. …", "Regards, …", "- Ravi") and addresses by unit numbers, street words, sectors and PIN codes; a bare name in the middle of a sentence is not detected (that would need an entity recogniser). The user id is the internal customer reference, not a name or email. Usage records cached input tokens where the provider reports them, and the M7 per-agent table shows a prompt-cache hit rate next to tokens and cost. Tail sampling: with `SHOPSENSE_TRACE_SAMPLE_RATE` below 1, a custom exporter holds each ticket's spans until its root span ends, keeps every trace with an error or a WARNING-level step (fallbacks, held or escalated tickets, failed checks) and keeps the given share of healthy traces, chosen by trace id so a trace is never half-kept; verified live (rate 0: the held ticket's trace arrived, the healthy one did not). The default 1.0 keeps everything.
- **Logging/observability:** Langfuse traces per ticket (session = ticket id, user = customer ref, tags = workflow); every LLM generation carries token usage and an estimated USD cost at list price (the free tier bills nothing, so this is what the same traffic would cost on a paid key; e.g. one intake parse: 729 tokens, $0.00034); fallback spans are WARNING-level so degraded traffic can be queried.
- **Rollback:** the system is stateless apart from `runtime/`; checkpoints are SQLite (swap for Postgres in production); tool writes are idempotent per ticket id.
- **Qdrant Cloud free clusters suspend when idle** — resume the cluster in the dashboard if retrieval fails with a TLS reset.
